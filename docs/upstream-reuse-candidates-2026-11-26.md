# 优先复用的实现：追加源码核查

日期：2026-11-26。用户要求先查成熟开源实现，避免继续自建已存在的能力。本轮只阅读上游代码，未修改正式播放器、未安装大型模型、未产生收费生成调用。

## EasyAIVtuber：此前遗漏的直接候选

项目：https://github.com/Ksuriuri/EasyAIVtuber

本轮直接读取README、`action_animeV2.py`、`alive.py`、`main.py`，而不只查看THA3底层模型说明。

- `ActionAnimeV2.speaking()`根据音量轨迹安排嘴部开合，叠加眨眼、视线和头部运动。与用户“不要求逐字口型”相符。
- `idle()`、`auto_blink()`、`eyeball_moving()`、`head_moving()`提供自动待机行为。
- `calc_cur_vector()`按当前时间从参数队列计算眼、嘴、头部参数，`calc_cur()`使用正弦插值。
- 状态变化时`reset_deque()`后由`check_deque()`从保存的当前参数安排约0.3秒回正，而不是将画面瞬间切到另一段视频。因此它有已经实现的状态衔接机制，不能被简单归类为没有解决切换问题的底层模型。
- `main.py`包含参数简化、按参数hash缓存生成帧和LRU淘汰、有限输出队列。已有优化策略应先评估复用，不能直接视为冷启动每帧都重新无缓存推理。
- 提供`POST /alive`的`speak`、`rhythm`、`sing`、`stop`、`change_img`等接口。可先以独立服务接现有TTS和事件业务，不必重新开发全部交互或虚拟摄像头。

不能扩大宣称的能力：

- 当前README推荐30系等显卡，仍使用PyTorch/CUDA；有限帧缓存不等于普通核显机器已经能运行。
- 当前动作集中在头部/脸部及有限身体运动，不等于已经有自然抬手、裙摆物理或全身鞠躬。
- 代码列有生气眉等底层参数，但已读自动调度中眉参数存在初始化为0的路径；不能据此说现成API已经有完整的情绪预设与任意组合。
- 输出以512像素模型为基础，放大输出尺寸不会自动增加细节。
- 本次仓库根目录树没有发现LICENSE；上游THA3的许可不能直接代替该项目全部新增代码的授权。实验、集成和商业再分发应分别判断。

## DH_live mini：应优先评估的低配候选

项目：https://github.com/kleinlee/DH_live

本轮补读`web_demo/README.md`，其部署示例明确以无GPU、普通2核4GB CPU为目标，数字人和VAD在Web端，TTS/ASR在服务端，LLM在云端；这是作者的部署描述，不是本项目低配测试结果。

已提供WASM、视频与逐帧数据的实际运行包，以及完整音频/前端实现。可以先直接运行原示例，再判断是否接入Electron；不应先自行重写WASM推理或脸部追踪。该项目本身支持localhost/WebCodecs，技术形态与现有客户端可对接。

需要验证二次元人脸、目标视频动作、素材预处理与商业素材授权。完整动作切换和开心/疑惑的独立控制不由单条“数字人可运行”说明保证。

## MatesX：区分可用应用代码与外部核心

项目：https://github.com/kleinlee/MatesX

应用层有Electron、前端加载、语音与对话代码；`preview/API.md`提供角色任务提交/查询，`MiniLive.js`加载视频与资源包，`MiniMateLoader_public.js`为WASM/Qt加载层。

README明确不提供底层算法实现，自定义角色涉及MatesX_key和其平台。它可作为现成产品/外部服务候选，但不能按“全部开源、完全自主免费部署”给出方案。

## 执行顺序

1. 针对现有目标角色，先分别运行EasyAIVtuber和DH_live原项目小样；比较自然开口、眨眼、头部动作、状态衔接与资源消耗。
2. 保留上游已有动作调度、预处理、输出或加载组件；优先接其公开接口，而不是先重写。
3. 表情、全身动作、低配和分发条件分别记录通过/未通过；只有缺失部分才考虑视频素材或其他组件补充。
4. 当前自写ActionPlayer和网格渲染不作为最终路线既定前提，先保留以免破坏已有工作，不继续扩大。
5. 用户若提供已知项目，优先核对该项目，避免用现有候选限制搜索范围。

这些候选尚未在目标机器运行。下一份结论应基于可复现的小样和明确版本，而不是再新增一个没有验证的“最终技术栈”。
