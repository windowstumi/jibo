# 二维虚拟主播技术栈与验收门槛

日期：2026-11-26。状态：架构建议与验证计划，尚未完成真实素材端到端验证，不作为已经验证的产品承诺。

## 完整需求

- 用户上传带背景、侧身等角色图，经标准化后生成该角色的直播素材，不要求用户提供手工分层PSD。
- 二维动漫/插画风；待机、说话、答谢、招手和介绍动作，包含可见表情、头发和服装自然运动。
- 嘴部有自然动作即可，不要求音素级同步；不使用脱离脸部的独立嘴贴图。
- 云端问答，商品知识约束，默认屏蔽词、无依据/不合适互动跳过，礼物语音答谢，主动循环讲解。
- 桌面客户端、Windows EXE及可迁移数据；其他OS分别构建和验收。OBS输出、抖音事件接入。
- 普通客户电脑不部署大型视频推理模型；生成成本和长期播出成本分开。
- 在确认完整技术路线和关键效果之前，不继续改造业务播放器。

## 重要边界

纯视频模式支持“素材中已有的动作与表情”，不能在一段视频上任意独立改变情绪、手势和口型。语义上可以分别记录这些标签，但播放时必须有匹配的完整素材，不能把标签当成独立动画轨道。

若要求运行时自由组合任意表情和动作，必须引入可参数驱动的模型、实时人脸处理或新视频生成。它们分别有模型制作、硬件/适配、生成延迟等成本。没有发现能同时消除这些成本的成熟开源产品。

因此，当前推荐的是**预生成有限但完整的动作/表情素材库**，并不承诺任意图片一次成功或任意动作随时生成。素材扩充不能被误称为零成本。

## 核心选型

### 制作端：云端生成、离线加工

| 模块 | 选择 | 理由与边界 |
| --- | --- | --- |
| 角色标准化 | 已配置的图片编辑服务，经统一模板提示词得到正面、固定构图的角色标准图 | 检查身份、服装、手脚和比例；保留原图与版本。输入不合适时允许拒绝/重做，不能保证所有侧身图都能可靠还原未见细节 |
| 完整动作与表情生成 | 优先验证Wan-Animate动作迁移；托管服务候选为万相图生动作 | 官方项目支持从参考视频同时迁移身体运动与面部表情。通过可重复使用的参考表演控制动作节奏；云API的实际参数、样片质量需单独验收，不等同本地开源模型行为完全相同 |
| 待机与说话素材 | 同一角色、镜头下制作自然循环的待机/说话参考表演；与其他动作使用共同回位姿态 | 通用说话嘴型不要求对应临时TTS内容；不能在讲话停顿时反复倒放或暂停整个人物 |
| 视频加工 | FFmpeg/ffprobe，以独立进程处理 | 统一尺寸、帧率、色彩、音轨与编码；裁剪多余停顿，校验时长和首尾。透明或绿幕处理先做实样检查；FFmpeg不能自动修复AI身份漂移 |
| 背景 | 独立背景素材＋人物透明/绿幕视频 | 避免多段完整背景分别生成后切换时背景跳变。透明视频边缘和绿幕颜色污染必须验收，绿色服装需其他抠像方案 |
| 素材封装 | 版本化JSON清单＋视频/背景＋校验值 | 客户端消费成品素材，不依赖生成服务私有返回格式 |

Wan-Animate官方依据：[项目页](https://humanaigc.github.io/wan-animate/)、[开源代码](https://github.com/Wan-Video/Wan2.2)、[预处理指南](https://github.com/Wan-Video/Wan2.2/blob/main/wan/modules/animate/preprocess/UserGuider.md)。项目页明确同时迁移表情与动作，预处理区分人脸和身体驱动信号。比例差异大时需重定向，并非参考视频随意选择都能成功。

### 播出端：维持现有基础，采用完整视频播放器

| 模块 | 固定选择 | 接口边界 |
| --- | --- | --- |
| 桌面外壳 | Electron | 主窗口、文件对话框、透明播出窗口、生命周期；各OS分别打包 |
| 本地业务 | Python/FastAPI＋SQLite | 商品/规则/事件/队列/素材索引；不处理实时视频模型推理 |
| 视频解码 | Chromium HTMLVideoElement | 优先有限视频槽和支持的硬件解码，不将全套素材解码成图片常驻内存；软解码回退需实测 |
| 合成与过渡 | WebGL | 人物抠像/透明合成、独立背景、两个完整视频之间的短时混合；不对预制视频叠加旧网格形变或独立嘴图 |
| 时序 | Web Audio/实际音频播放事件＋视频帧回调 | 明确的语音开始/结束/取消和动作完成，不能让UI状态或生成完成事件代替实际开始播放 |
| 语音 | 现有TTS接口；Windows系统语音兜底，CPU ONNX或云TTS经试听选定 | 统一返回可缓存音频，固定讲稿缓存；语气配置只使用该服务实际支持的能力 |
| 问答 | 云端兼容Chat Completions＋本地商品检索与输出校验 | 内容、表现标签在审核后进入播出计划；礼物用模板；不让观众指令直接选动作、表情或越过商品约束 |
| 对外播出 | OBS采集现有播出窗口/受控浏览器源 | 不复制OBS代码，不把其插件作为用户必须额外安装的内部依赖 |
| 平台事件 | 外部采集程序归一化为已有事件协议 | event_id、kind、username、text/gift/count；鉴权、去重、过期、重连状态。真实抖音采集连通性是独立上线门槛 |
| 打包 | 现有PyInstaller＋electron-builder | 运行时依赖/用户数据分离；不附带CUDA、PyTorch、视频生成权重 |

这套选型使更换视频供应商只影响制作端；新增表情和动作主要增加素材与清单；更换TTS只影响配音适配。不能保证未来永不修改代码，但能避免生成服务或某个模型格式直接贯穿商品业务和播出流程。

## 素材与行为约定

素材记录至少包括：id、角色版本、文件、校验值、状态（idle/talk/gesture）、情绪标签、动作标签、是否循环、起止姿态、安全进入/退出时间、是否包含嘴部运动、背景/透明方式、分辨率/帧率、质量审核状态。语气、表情和动作标签需分开命名，但不得假定可自由组合。

播出计划包括：已审核文本、音频、语气、情绪、动作意图和语句边界。语气决定声音选择/风格（若TTS支持），情绪和动作从本角色已有素材中选择；缺少匹配素材时有明确降级，不能播放明显冲突的素材。

建议首轮验证不做完整笛卡尔积，而覆盖以下关键组合：

| 素材 | 口部 | 表情/身体 | 目的 |
| --- | --- | --- | --- |
| neutral-idle | 闭嘴 | 平静、呼吸、眨眼、头发/衣料轻动 | 待机循环 |
| neutral-talk | 自然开合 | 温和说明、轻微身体运动 | 商品讲解/普通问答 |
| happy-talk | 自然开合 | 明显开心但不过度夸张 | 开心语音与表情一致性 |
| thoughtful-talk | 自然开合 | 思考/疑惑，保持可读性 | 证明表情不仅有微笑一种 |
| thanks | 根据表演，可闭嘴 | 微笑＋点头/小幅鞠躬＋回位 | 答谢动作与表情同时存在 |
| greeting | 根据表演，可闭嘴 | 微笑＋招手＋回位 | 手指、肩袖和动作自然度 |
| present | 根据表演 | 介绍手势＋友好表情＋回位 | 商品展示动作 |

动作中若只是播放通用开口画面，可以同时播放语音，但明确不做音素级同步；闭嘴鞠躬等素材按语句边界安排。绝不把“能叠加音频”说成已经实现精确口型。

纯视频的情绪切换也需要安全出口。任意姿态上直接混合会出现重影，所以素材要有共同回位姿态和可切换时间；等待上限、降级策略和语音首句延迟必须一起设计。

## 开源实现如何使用

- **Wan-Animate**：作为动作＋表情生成技术的主要验证对象；部署在制作端或用托管服务，不交给每个客户电脑运行。
- **LiveTalking**：参考音频标签、动作优先级、取消、统一时钟；其说话分支仍有实时推理，不整体作为低配纯视频播放引擎。
- **OBS/Advanced Scene Switcher**：参考媒体结束、循环、预加载、过渡等成熟行为；不把源码直接拼进闭源产品。
- **DH_live mini**：保留为人脸处理候选，不作为本方案前置依赖。它的逐帧坐标与WASM处理不等同预制视频，也还未验证二次元适配。
- **Talking Head Anime 3**：新增核对的受限候选，可由单张标准动漫图控制表情、头部、身体和呼吸；512×512、透明、正面输入等限制，不提供自然大幅全身动作，官方要求较强NVIDIA GPU。只适合作为离线生成表情素材的备选实验，不作为必须组件。[官方README](https://github.com/pkhungurn/talking-head-anime-3-demo)声明代码MIT、权重CC BY 4.0，分发需遵守署名等条件。

## 决定是否进入业务改造的验收门槛

1. **生成能力**：同一目标角色至少取得自然待机、自然说话、开心/疑惑表情及招手/答谢实样。检查身份、服装、背景、肢体、裙摆；不以静态测试视频代替AI效果。
2. **切换能力**：待机→说话→开心→答谢→待机连续播放；检查重影、黑帧、裁切、循环接缝。失败时区分素材问题与播放问题。
3. **表达能力**：不要求逐字口型，但语音期间有嘴部动作，语音结束不会持续长时间张嘴；开心/疑惑可见且不会由不合适弹幕直接触发。
4. **业务能力**：商品知识问答、无关/屏蔽互动跳过、礼物答谢、主动讲解恢复；语音与动作排队不重复、不争抢。
5. **低配能力**：在目标普通电脑测720P/30FPS、单活跃解码＋切换时第二解码、端到端首句延迟、CPU/GPU/内存与2小时稳定性。8GB内存＋核显是待测目标，不是已经承诺的最低配置。
6. **分发能力**：新路径Windows EXE、素材导入导出；需支持的macOS/Linux分别构建验收；资源和供应商配置不写死到开发者机器。
7. **平台能力**：真实授权直播间的弹幕、礼物、重连、去重与OBS声画采集；当前只有预留事件接口不能算已完成接入。

以上关键效果验证未通过前，不宣称完整技术栈已验收，不以扩大功能数替代验证。读取官方资料确认模型能力，不等于已经证明它适用于用户的角色图。

## 本轮结果

已确定推荐的架构边界、主要技术候选和验收组合；未更改业务播放器，未提交或购买视频生成任务，未保证任何供应商在任意图片上一次成功。下一步需要做的是这条固定路线的真实素材样例和隔离播放器验证，而不是再次更换整个客户端技术栈。
